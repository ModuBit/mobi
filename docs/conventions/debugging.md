# 调试与修改规范

适用于所有包、所有场景的通用方法论。

## 1. 先观测后动手

遇到问题，**禁止凭推理直接改代码**。先采集运行时数据，从数据中定位根因，再针对性修改。

推理可以产生假设，但假设必须用数据验证。未经数据验证的推理直接改代码 = 盲改。

## 2. 整体规划，一次改完

一个问题涉及多个互相关联的现象时，动手前必须：
- 列出所有现象
- 逐个分析根因
- 确认各修复方案之间不冲突
- 一次性实施

头痛医头、改一个坏一个，成本远高于停下来先规划。

## 3. 同一类方法失败两次就换思路

连续两次用同类型方法尝试都失败，说明方向错了。不要用同一种思路第三次尝试。

可以换观测角度、换实现方式、回滚重来。不要在失败的路线上持续投入。

## 4. 每次改动后立即验证

改完一处 → 立即验证。验证失败 → 立即回滚，不要在失败的改动上继续叠补丁。

小步前进，每次只改一个点，确认无误后再改下一个。

## 5. 用户重复提醒同一件事时，停下来

用户两次以上表达同样的意思（"把所有问题放在一起考虑"、"不要再犯同样的问题"），说明当前方向或方法有问题。必须停下来，重新理解用户的诉求，而不是加速执行。

## 6. Web 渲染链路诊断埋点（diag）

「工具卡片不渲染 running 态」类问题 E2E 难以复现（依赖历史会话/审批时序等前置状态）时，用常驻诊断埋点回读现场数据，替代反复复现。见 `packages/web/src/core/lib/diag.ts`。

- **开启**：URL 加 `?diag=1`，或 localStorage 置 `mobi-diag-enabled=1`（下次加载自动开）。全构建可用，默认关
- **移动端（PWA）**：创建页连点品牌 Logo ≥5 次解锁设置页调试区块，可开关埋点 + 一键下载诊断数据
- **取数据**：bug 出现后控制台 `window.__mobiDiag.dump()`（或 `copy(...)`）。刷新/关页数据仍在（localStorage 镜像），无需预装
- **数据形态**：`events` 事件序列 + `tools` 按 tool_use_id 聚合的状态史（snapshot 到达 → 建块/状态迁移 → 渲染），可定位卡在渲染链路哪一环
- **管理**：`window.__mobiDiag.clear()` 清空；`disable()` 关闭并清数据
