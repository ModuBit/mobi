# 注释规范：决策留痕

适用于所有包。本规范只管一类注释：**解释「为什么」的注释**。它不要求给普通代码写注释——复述代码在做什么的注释一律不写。

灵感来源：ZCode 源码的注释实践（调研见 `docs/research-zcode-interactions.md`）——几乎每个反直觉实现都附「为什么」，多处给出 profile 证据和演化史，可维护性本身就是交互质量。

## 1. 反直觉实现必须留「为什么」

当一段代码的做法与直觉相悖（看起来能更简单但故意没这么做、看起来该用某组件但弃用了、数字看起来随意但其实是调过的），必须在注释里写清原因。判断标准：**未来维护者看到这段代码，会不会想"为什么不直接 XXX"？会，就必须写。**

```ts
// 运行态不用旋转 spinner：流式期间工具卡数量多且持续更新，
// 旋转 loading 会长期占用渲染资源，改用静态图标 + 文字扫光。
```

反面例子：`// 兼容处理`、`// workaround`、`// 特殊情况`——这类注释等于没写，禁止。

## 2. 动画必须有语义注释

动画不是装饰，是状态表达。每个动画必须回答两个问题，写在其实现处：

- **它表达什么状态？**（"心跳属于正在运行的站灯，行进光表达的是过去——光是不动的"）
- **页面上同时在动的东西是哪些？** 一屏内持续运动的元素应尽量只有一个；多处同时动 = 用户不知道看哪。

改动画语义时，把演化史留在注释里：

```css
/* 行进边改前是一条沿路径滚动的虚线，读起来像"还在赶路"——
   但这条边表达的是控制流已经走过（过去时），动态属于当前运行站的心跳。 */
```

## 3. 性能决策必须附证据

因为性能原因放弃某个方案（弃用某组件库、不做虚拟化、加缓存、限制重渲染）时，注释必须给出**可复现的测量**，不接受"感觉会慢"：

```tsx
// 弃用 Radix Collapsible：几十个实例会让 click 出现 600ms+ long task
// （Chrome DevTools Performance 面板实测，见 2026-09 会话记录）。
// 每行就是普通按钮，仅展开行渲染内容。
```

证据的最低要求：数字（耗时/帧率/条数）+ 复现路径。测量数据来自 `docs/conventions/debugging.md` 的诊断手段（Performance 面板、diag 埋点）。

## 4. 时序类代码必须写清前提

涉及「谁先谁后」的代码（effect 依赖顺序、首拉与 SSE 竞态、卸载时机、动画与卸载的时序窗口）必须注释说明依赖的时序前提，因为这类 bug 的根因恰恰是前提不可见：

```ts
// 前提：此 effect 必须晚于首拉完成，否则 SSE 早到的增量会被 setQueryData 覆盖。
// 见 project_first-fetch-race-pattern。
```

## 5. 「为什么」放注释，不是放 commit

判断标准：**未来读代码的人需要的信息放注释，只在 review/溯源时需要的信息放 commit message。**

- 放注释：这个分支为什么存在、为什么不用更显然的方案、约束前提、踩坑史。
- 放 commit：改了什么、关联哪个 ticket、测试怎么验证的。

同一条信息两处都需要时，注释写全，commit 引用即可。

## 6. 注释的维护义务

- 改到某段代码时，其注释必须同步核对——**过期的「为什么」比没有更毒**（它把读者引向错误的历史）。
- 注释描述的是当前约束还是历史事实，用措辞区分：「此前是 X，因 Y 改为 Z」（历史）vs「必须保持 X，否则 Y」（现行约束）。
- 删除代码时，如果它解释的约束仍然成立（比如"为什么不用某方案"），把注释迁到替代实现上，不随代码一起删。

## 7. 不写什么

- 复述代码的注释（`// 设置状态为 running`）。
- 无上下文的 TODO（写 TODO 必须带"谁/什么时候/做什么"，或直接进 `docs/pending.md`）。
- 表达歉意的注释（"临时方案，抱歉"）——要么说清约束和退出条件，要么不写。
