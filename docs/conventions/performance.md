# 性能工作规范

适用于所有包的性能优化与性能基准工作。方法论来源：Anthropic《How we made claude.ai 3x faster in two weeks》（2026-09-23）的工程文化提炼，结合 mobi 本地实例；完整调研见 [docs/research-claude-ai-perf.md](../research-claude-ai-perf.md)。

## 1. 基准必须先证明与体感相关，否则拆掉

任何性能基准（指令计数、commit 数、帧预算、计时器）在成为门禁之前，必须先回答一个问题：**对它爬坡，真机体感/墙钟时间是否跟着变好？** 证明不了相关性的基准直接下线，不许围绕它持续优化。

- 原因：代理（人或 Claude）会爬它面前的任何数字。flaky 或与体感无关的数字会把优化引向错误的山头。
- 本地实例：web 全量测试曾出现 ~400s 劣化（机器压载噪声），真实基线 ~40s——墙钟类噪声数字不能当门禁；确定性计数（如纯函数指令数）才有资格进 CI 棘轮。
- 操作顺序：建基准 → 一次相关性验证（降数字 → 真机/墙钟确认变好）→ 通过才挂 CI；验证不过就撤基准，不留「看起来有用」的假指标。

## 2. 复杂度预算与毫秒收益对表

动手优化前先对两个数：**预期省多少毫秒（或多少 % 帧预算/长任务），花多少行/多少架构复杂度**。收益对不上复杂度的，记进 [docs/pending.md](pending.md) 观望，不当场做。

- 参照判例：「900 行换 2ms/send」被一句话否决。
- 用户可感知的交互权衡（骨架屏何时出现、内容逐格还是逐行出现、动画值不值帧预算）不属于此条——那是 Taste 决策，交给人裁决，机器只管把毫秒省出来。
- 用此标准筛过一轮的「暂不做」清单见 [docs/research-claude-ai-perf.md](../research-claude-ai-perf.md) 第三节。
